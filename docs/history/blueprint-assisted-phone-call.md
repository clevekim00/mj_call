# 말이음 통화 도우미 — 제품 기획 및 구현 Blueprint

> 작성: 2026-11-01 · 갱신: 2026-11-02 · 상태: 제품 기획 및 수동 통화 보조 1차 구현
> 사용자 요청: 통화할 곳과 목적을 입력하면 기기가 대신 대화하고, 목적 달성 여부와 녹음을 남긴다.
> 사용자 확인: 별도 스마트폰의 스피커폰 + 아이패드 또는 PC. 첫 지원 대상은 기관·고객센터 문의.
> 가정: 한국어·국내 사용. 구체적인 첫 기관과 지원 기기는 추가 선정한다.
> 1차 구현: 오늘 화면 진입, 문의 준비 저장, 직접 입력·준비 문장 한국어 TTS, 선택적 녹음, 재생·삭제, 수동 결과 기록. AI 자동 대화·상대 음성 인식은 향후 범위다. 실제 통화 실험은 수행하지 않았다.

## 0. Goals and Deliverables

### Primary Goal
마비말장애 사용자가 말하기 부담 때문에 타인에게 맡겨야 했던 일상 통화를 스스로 시작하고, 자신의 의도와 허용 범위 안에서 마칠 수 있게 한다. 임상적 말하기 훈련과 별도의 생활 의사소통 지원 기능으로 제공한다.

### Success Definition
- 사용자가 상대·목적·허용 조건을 입력하고 직접 발신한다.
- AI는 허용 조건 안에서 질문과 답변을 이어가며, 새로운 결정은 사용자에게 묻는다.
- 날짜·시간·장소·비용 등 필수 항목을 상대에게 재확인한다.
- 결과를 성공 / 부분 달성 / 미달성 / 확인 불가로 구분하고 근거 발언과 연결한다. 통화가 끝났다는 이유만으로 성공 처리하지 않는다.
- 녹음을 선택한 경우, 저장 성공 여부와 누락 구간을 사용자에게 명확하게 알린다.
- 기관 문의는 사전에 정한 질문의 답, 필요한 서류·신청 방법·기한·담당 부서 등 해당되는 항목을 확인해야 완료다. 상담원 연결이나 문의 접수만 된 경우 최종 해결과 구분한다.

### Out of Scope
- 첫 버전: 자동 발신·전화기 원격 조작·자동 재발신·수신 전화 자동 응대 제외.
- 응급 신고, 금융 거래, 계약 체결, 진료 판단, 유료 결제, 본인 인증 대행 제외. 병원은 일정 문의·예약으로 한정한다.
- 모든 환경에서의 동시 발화 인식 및 양측 음성의 완전한 분리 녹음 보장 제외.
- 마비말장애 음성을 반드시 인식해야 사용할 수 있는 설계 제외. 글·선택 버튼을 기본 입력으로 한다.

## 1. Working Context

### Background
스피커폰 전화기 옆에서 보조 기기가 듣고 말하면 기존 전화번호와 통신사를 유지하면서 시작할 수 있다. 통신망 연동 이전에 수요를 검증하기에 적합하다. 다만 전화기와 보조 기기의 두 오디오 처리 체인이 서로 영향을 주므로, 단일 기기의 음성 챗봇보다 실환경 음향 검증이 중요하다.

기존 대안으로 Apple Live Speech는 입력한 글을 통화 중 음성으로 전달하고, 손말이음센터는 문자·음성 중계를 제공한다. 제안 기능의 차별점은 목적·허용 조건을 기억하는 대화 진행, 결정 시 사용자 개입, 결과의 근거 확인이다. 기존 대안 대비 편의성·신뢰성이 실제로 나아지는지 검증해야 한다. [Apple 접근성](https://www.apple.com/accessibility/features/), [손말이음센터 서비스 소개](https://mail.relaycall.or.kr/user/info/service).

### Objective
목적 기반 대화를 작은 범위부터 검증한다. 제품의 핵심 질문은 ‘자연스럽게 말하는가’에 더해 ‘사용자가 원하는 조건을 보존하면서 상대에게 필요한 정보를 전달하고 결과를 확인하는가’이다.

### Scope
- 포함: 통화 준비, 기기 배치 점검, 목적 기반 대화, 큰 선택 버튼, 직접 입력해 말하기, 녹음 선택, 결과 확인.
- 초기 통화 유형: 기관의 이용·신청 절차, 필요 서류·기한·담당 부서 문의, 고객센터의 일반 이용 방법·문의 접수 및 처리 절차 확인.
- 계정별 조회·민원 접수는 기관이 대리 발화 방식을 수용하고 허용된 정보만으로 진행할 수 있을 때 지원한다. 본인 인증이 필요한 경우 자동 진행을 중단한다.
- 진행 모드: 직접 입력해 말하기 → AI 추천 문장 승인 → 사전 허용 조건 내 자동 대화.
- 자동 대화에서도 신청·취소·민원 접수·새 비용 동의처럼 상태를 바꾸는 행위는 사용자 확인을 받는다. 단순 인사·준비된 사실 전달·절차 질문은 자동화한다.
- 첫 버전 ARS는 안내 자막과 선택 번호 추천을 제공하고, 번호 입력은 사용자가 전화기에서 수행한다. 실제 버튼 입력과 성공 여부를 앱이 확인한 것으로 간주하지 않는다.
- 향후: 통신망 연결 방식, ARS 자동 조작, 예약·일정 변경 템플릿. 별도 단계로 평가한다.

### Inputs
| Item | Format | Source | Notes |
|---|---|---|---|
| 전화할 곳·전화번호 | 텍스트 | 사용자 | 발신은 사용자가 전화기에서 수행 |
| 목적·완료 조건 | 템플릿 + 자유 입력 | 사용자 | 예: 신청 서류·제출 방법·접수 기한 확인 |
| 허용 조건 | 날짜 범위·시간·인원·비용 상한·금지 사항 | 사용자 | 새로운 조건에 자동 동의하지 않음 |
| 전달 정보 | 이름·연락처 등 선택 항목 | 사용자 | 상대에게 전달할 항목별 허용 |
| 통화 음성 | 마이크 스트림 | 보조 기기 | 전화기 스피커 소리를 공기로 수음 |
| 녹음·클라우드 처리 선택 | 별도 선택 | 사용자 | 저장과 AI 전송을 구분 |

### Outputs
| Item | Format | Destination | Notes |
|---|---|---|---|
| 발화 | 합성 음성 + 표시 문장 | 스피커·화면 | 전화기 마이크가 수음 |
| 대화 기록 | 시각·텍스트·불확실 표시 | 기기 저장소 | 인식 문장은 수정될 수 있음 |
| 결과 | 구조화 항목 + 근거 시각 | 결과 화면 | 미확인 항목 구분 |
| 녹음 | 마이크 음원 + AI 출력 음원·재생 시각 | 기기 저장소 | 공기 전달 이후 상대가 실제 들었음을 증명하지는 못함 |

### Constraints
**음향:** 보조 기기의 합성 음성이 다시 마이크에 들어오고, 전화 회선을 거쳐 돌아올 수도 있다. 보조 기기의 출력 신호를 참조하는 에코 제거와 재인식 억제가 필요하다. OS의 에코 제거만으로 이중 경로가 해결된다고 가정하지 않는다. 초기에는 듣기/말하기를 번갈아 수행하되, 발화 중 겹친 상대 말은 놓칠 수 있음을 처리한다. 겹침 감지 시 발화를 멈추고 재확인하며, 자기 목소리로 잘못 중단하지 않는지도 시험한다. [W3C 미디어 캡처 규격](https://www.w3.org/TR/mediacapture-streams/), [Apple voiceChat](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/voicechat).

**플랫폼:** ‘아이패드 이상’은 성능 기준이 아니다. 지원 OS·기기·브라우저 조합을 실측해 정한다. 아이패드 앱 + Windows/macOS 브라우저를 목표로 하고, PC 네이티브 앱은 필요할 때 추가한다. 브라우저는 HTTPS·마이크 권한·사용자 재생 시작이 필요하며, 잠금·탭 이동·백그라운드 전환은 초기 지원에서 제한한다. 마이크 사용 중 스피커 음량과 출력 경로 변화도 검증한다.

**기기 역할:** 실제 전화 연결과 종료는 스마트폰에서 한다. 보조 앱의 ‘즉시 말하기 중지’는 합성·생성 대기열을 취소하고 이후 자동 발화를 막지만 전화를 끊지는 않는다. 전화가 끝났는지도 사용자가 최종 확인한다. 주변 소리만으로 연결·종료 상태를 확정하지 않는다.

**네트워크:** 직접 입력·준비 문장 발화는 지원 음성이 설치된 경우 로컬 동작을 목표로 한다. AI 자동 대화는 초기에는 온라인을 가정한다. 네트워크 단절 시 발화를 멈추고 준비된 안내 문장과 직접 입력 모드로 전환한다.

**동일 기기 방식:** Apple은 지원 환경에서 합성 음성을 통화에 넣는 API를 제공한다. 따라서 ‘같은 기기에서는 무조건 불가능’하다고 단정하지 않는다. 다만 이 API가 상대 음성을 읽거나 통화 전체를 녹음하는 권한까지 제공하는 것은 아니므로, 완전한 대화 자동화 가능성은 별도 확인한다. [Apple 합성 음성 통화 전달](https://developer.apple.com/documentation/avfaudio/adding-synthesized-speech-to-calls).

**녹음·개인정보:** 한국의 타인 간 대화 녹음 금지 규정과 개인의 당사자 녹음, 서비스 사업자의 클라우드 처리·보관은 구분해야 한다. 사용자가 통화에 참여하더라도 이 서비스 구조 전체의 적법성이 자동 보장된다고 보지 않는다. 출시 전 당사자성·대리 발화·음성 처리·위탁·국외 이전·민감정보 처리 근거를 검토한다. 상대 안내·녹음 허락은 제품 정책으로 설계하며 이를 모든 경우에 적용되는 법적 의무라고 단정하지 않는다. [대법원 2023도8603](https://portal.scourt.go.kr/pgp/main.on?c=900&jisCntntsSrno=3314865&w2xPath=PGP1011M04), [개인정보 보호법](https://www.law.go.kr/LSW/lsInfoP.do?ancYnChk=0&chrClsCd=010202&efYd=20260911&joNo=002808&lsiSeq=283839&urlMode=lsInfoP).

- 첫 인사 예: ‘사용자가 옆에서 내용을 확인하며 음성 도우미로 대화하고 있습니다.’ 장애명은 사용자 선택 없이 공개하지 않는다.
- 녹음은 매 통화 선택한다. 안내·허락 전에는 영구 녹음하지 않고, 거절 시 버퍼를 폐기한다. 실시간 AI 처리 자체를 거절하면 저장 중지만으로 해결하지 말고 자동 청취도 중단한다.
- 서버는 지속 녹음 보관을 기본으로 하지 않는다. 모델 공급자의 보존·학습·전송 지역을 확인하고 표시한다. 로컬 저장만 해도 클라우드 음성 처리가 있다면 ‘외부 전송 없음’으로 표시하지 않는다.
- 녹음·전사·요약·백업의 삭제 범위를 함께 설계한다. 기본 보관기간은 30일을 초안으로 두고 사용자 확인 후 확정한다. 학습용 재사용은 기본 비활성화한다.

| Term | Definition |
|---|---|
| 보조 기기 | 대화를 듣고 합성 음성을 출력하는 아이패드·PC |
| 목적 달성 | 필수 항목이 상대 발언으로 확인되고 사용자 조건과 일치하는 상태 |
| 허용 범위 | AI가 추가 질문 없이 전달하거나 선택할 수 있는 사전 설정 |

### 사용자 경험과 화면
#### 메뉴 진입 위치
현재 기본 메뉴 ‘오늘 → 훈련 → 게임 → 기록 → 설정’을 유지하고 **오늘 화면의 상단 주요 카드 ‘통화 도우미’**를 추가했다. 훈련을 거쳐야 이용하는 구조로 두지 않는다. 상세 사용법과 검증 제한은 [통화 도우미 구현 안내](docs/call-assist.md)에 정리한다.

- 경로: **오늘 → 통화 도우미 → 새 통화 준비 → 기관·고객센터 문의**.
- 통화 도우미 첫 화면: ‘새 통화 준비’, ‘준비한 문의’, ‘최근 통화’. 처음에는 진행할 수 있는 버튼을 가장 크게 표시한다.
- 준비한 문의는 기관·질문·공개 허용 정보를 다시 확인한 뒤 재사용한다. 이전 통화의 신청·정보 공개 승인을 새 통화에 자동 승계하지 않는다.
- 기록 메뉴: 1차 구현은 상단 ‘통화 기록’ 전화 아이콘으로 통화 도우미 기록 화면에 연결한다. 통합 ‘통화’ 필터와 자동 전사는 후속 범위다. 통화 도우미의 최근 통화도 같은 기록을 사용한다.
- 설정: ‘통화 도우미 → 목소리·말하기 속도 / 녹음·보관 / 외부 AI 처리 안내’. 녹음과 정보 공개는 실제 통화 준비에서도 확인한다.
- 사용 빈도가 높아지면 독립 하단 메뉴 도입을 평가한다. 초기에는 기존 하단 메뉴에 여섯 번째 탭을 추가하지 않는다.

#### 음성 지원 방식
| 구분 | 첫 버전 제안 | 제한·실패 처리 |
|---|---|---|
| 사용자의 의도 입력 | 키보드·문의 템플릿·큰 선택 버튼이 기본, 선택적 음성 입력 | 마비말장애 음성 인식 성능을 보장하지 않는다. 인식한 글을 수정·확인한 뒤 사용 |
| 상대 말 듣기 | 보조 기기 마이크가 전화기 스피커 소리를 받고, 한국어 스트리밍 STT로 문자화 | 불명확한 날짜·숫자·고유명사는 되묻기. 인식 실패를 임의 보완하지 않음 |
| 대신 말하기 | AI가 답변 문장을 만들고 정책·승인 검사 후 한국어 TTS로 출력 | 상대 말 그대로 따라 읽거나 생성 즉시 무검사 발화하지 않음 |
| 직접 입력해 말하기 | 사용자가 입력한 문장·준비 문장을 TTS로 재생 | 온라인 AI가 끊겨도 설치된 로컬 한국어 음성으로 가능한 범위를 제공 |
| 통화 녹음 | 선택한 통화의 마이크 음원과 AI 출력 음원·재생 시각 보관 | 전화 회선 원본 녹음이 아님. 상대 말과 주변 소리가 섞일 수 있음 |

처음에는 일반 합성 목소리 2~3개를 목표로 하되, 실제 지원 개수는 공급자·OS별 한국어 음질을 검증한 후 확정한다. 이름이나 성별보다 직접 들어 보고 고를 수 있는 미리듣기를 제공한다. 말하기 속도와 출력 음량을 조절하고, 날짜·번호는 짧게 끊어 읽는다. 사용자의 목소리를 녹음해 복제하거나 사전 음성 훈련을 완료할 필요는 없다. 개인 음성 복제는 첫 버전에서 제외한다.

자동 대화는 한국어 STT·LLM·TTS를 서버로 연결하는 온라인 방식을 기본으로 설계한다. PC와 아이패드에서 같은 클라우드 TTS를 쓰면 목소리를 일관되게 유지하기 쉽다. 로컬 대체 음성은 OS별로 달라질 수 있으므로 전환 상태를 표시한다. 공급자·가격·음질·보존 정책은 미선정이며 계약이나 성능 보장이 아니다.

음성 입력을 사용하지 않아도 통화 전 과정을 마칠 수 있어야 한다. 말하기 중지 버튼은 현재 출력뿐 아니라 생성 중인 후속 문장도 취소한다. 사용자가 직접 말하려면 ‘직접 말할게요’를 선택해 AI 출력을 멈춘다. 전화기 마이크는 그대로 켜져 있으므로 사용자의 실제 목소리도 상대에게 전달될 수 있음을 안내한다.

#### 통화 화면 흐름
1. **준비:** 전화할 곳 → 할 일 → 원하는 조건 → 전달 정보. 한 화면의 필수 입력은 최소화하고 이전 준비 내용을 재사용한다.
2. **소리 점검:** 두 기기를 나란히 놓고 시험 문장을 재생한다. 처음에는 조용한 방에서 배치를 안내하되 거리·음량은 실험으로 정한다.
3. **시작:** 사용자가 전화기에서 발신·스피커폰을 켜고, 상대 응답 후 앱에서 ‘대화 시작’을 누른다.
4. **진행:** 상단에 목적·조건, 중앙에 상대 말과 AI 발화, 하단에 ‘예 / 아니요 / 다른 조건 / 직접 입력 / 잠시 기다려 주세요 / 즉시 말하기 중지’를 고정한다. 듣는 중·생각 중·사용자 선택 대기·말하는 중·녹음 중 상태를 구분한다.
5. **결정:** 상대가 다른 시간을 제안하면 큰 선택 카드로 제시한다. 답변 제한시간을 강제하지 않고, 사용자가 원하면 대기 요청을 발화한다. 동일한 대기 문장을 반복 송출하지 않는다.
6. **마무리:** AI가 확정 조건을 되읽고, 사용자가 실제 통화를 종료한 뒤 결과·녹음·다음 할 일을 확인한다.

키보드·스위치 입력·스크린리더·글자 확대·가로 화면을 고려한다. 빠른 손 조작이나 음성 입력을 필수로 하지 않는다. 청취가 가능하면 상대 말을 직접 듣는 것을 유지하고 자막은 보조 수단으로 제공한다.

### 예시 시나리오
목적: ‘기관에 서비스 신청에 필요한 서류, 온라인 신청 가능 여부, 접수 기한을 물어봐 주세요. 신청 자체는 하지 마세요.’
ARS 안내를 들은 앱이 ‘신청 안내는 2번으로 안내되었습니다’라고 표시하면 사용자가 전화기에서 누른다. 상담원이 연결되면 AI가 준비한 질문을 하고, 안내받은 서류·방법·기한을 되읽어 확인한다. 다른 부서로 전환되면 지금까지의 문의를 짧게 다시 전달한다. 주민등록번호나 인증번호가 요구되면 자동 전달하지 않고 사용자가 처리할 수 있는 대안을 묻는다. 담당 부서 연결만 됐거나 회신 예정이면 ‘부분 달성·회신 대기’로 남긴다.

### 기관·고객센터 통화의 추가 요구사항
- **대기 모드:** ARS·보류 음악·안내 방송에 답변하지 않는다. 상담원 인사로 추정되는 구간에서 대화를 재개하되 오판 시 즉시 중지할 수 있어야 한다. 상담원 연결 자동 감지가 불확실하면 사용자 시작 버튼을 사용한다.
- **장시간 대기:** 전체 통화 시간과 실제 AI 처리 시간을 구분한다. 대기 중에도 음성 감지·인식 비용이 발생할 수 있으므로 비용을 측정하고, 대기 제한은 사용자가 설정한다. 제한 도달 시 알리고 계속 대기 여부를 받으며 자동 종료하지 않는다.
- **담당 부서 전환:** 이전 답변과 미답변 질문을 유지한다. 전환 안내만으로 새 상담원이 연결됐다고 확정하지 않는다.
- **조회·인증:** 일반 절차 안내부터 시작한다. 본인만 가능한 업무나 대리 발화 거절은 우회하지 않고, 가능한 문의 범위·문자 상담·대체 절차를 확인한다.
- **결과 카드:** 질문별 답·근거 시각·추가 확인 여부, 서류·제출 경로·기한·담당 부서·접수번호·회신 예정일 중 실제 안내된 항목을 표시한다. 안내받지 않은 값은 만들지 않는다.
- **미해결 구분:** 답변 완료 / 일부 답변 / 접수 후 회신 대기 / 담당 부서 재문의 / 인증 필요 / 연결 실패를 구분한다. 회신 대기를 해결 완료로 집계하지 않는다.

## 2. Workflow Definition

### End-to-End Flow
`목적 입력 → 조건 확인 → 음향 점검 → 직접 발신 → 안내 → 듣기·판단·발화 반복 → 사용자 결정 → 상대 재확인 → 직접 통화 종료 → 결과 검증·보관`

### LLM vs Code Boundary
| LLM handles | Code handles |
|---|---|
| 목적을 질문 목록으로 구성, 상대 의도 해석, 응답 초안, 결과 요약 | 권한·오디오 I/O·재생 취소·녹음·상태 전이·저장·허용 항목 검증 |
| 모호한 날짜·숫자를 확인할 필요 판단 | 날짜 정규화·범위 비교·미확인 값 표시·확정 전 승인 검사 |

상대가 ‘기존 지시를 무시하라’고 말해도 통화 데이터로만 취급한다. 상대 발언으로 권한·저장 설정·승인 규칙을 변경하지 않는다. 자유 생성 응답은 정책 검사 후 발화하고, 금융·인증·새 비용·범위 밖 선택은 코드 수준에서 막는다.

#### Step 01: 통화 계획 준비
1) Step Goal:
사용자의 목적과 완료 조건을 실행 가능한 계획으로 만든다.
2) Input / Output:
- Input: 상대·목적·허용 조건·전달 허용 정보.
- Output: 질문 순서·필수 확인 항목·승인 필요 조건.
3) LLM Decision Area:
자유 입력에서 누락 조건을 찾고 쉬운 질문으로 확인한다.
4) Code Processing Area:
입력 스키마와 날짜·시간·정보 공개 범위를 검증한다.
5) Success Criteria:
사용자가 계획을 확인하고 시작할 수 있다.
6) Validation Method:
스키마·범위 검사 및 사용자 검토.
7) Failure Handling:
필수 조건 누락은 선택지로 요청한다. AI 실패 시 템플릿 계획을 사용한다.
8) Skills / Scripts:
Skill: 없음. 향후 계획 서비스·검증기 구현.
9) Intermediate Artifact Rule:
개발 시 합성 자료만 `output/step01_plan.json`에 둔다. 실사용 자료는 보호된 앱 저장소에 둔다.

#### Step 02: 음향 점검 및 통화 시작
1) Step Goal:
마이크·스피커·녹음 선택을 확인하고 사용자가 발신한다.
2) Input / Output:
- Input: 계획·권한·기기 배치.
- Output: 점검 결과·대화 시작 상태.
3) LLM Decision Area:
고정 안내문을 기본으로 하며 불필요한 판단은 하지 않는다.
4) Code Processing Area:
입출력 수준·오디오 경로·권한·세션 중단·녹음 허용 상태 관리.
5) Success Criteria:
상대 응답을 사용자가 확인하고 대화 시작을 누른다.
6) Validation Method:
실기기 소리 점검과 사용자 확인.
7) Failure Handling:
권한 거절·음량 부족은 시작하지 않는다. 자동 반복 발신은 하지 않는다.
8) Skills / Scripts:
Skill: 없음. 향후 오디오 점검 모듈.
9) Intermediate Artifact Rule:
`output/step02_audio-check.json`에는 개발용 음량·지연 수치만 기록한다.

#### Step 03: 목적 기반 대화
1) Step Goal:
목적에 필요한 정보를 주고받고 새로운 결정은 사용자에게 돌린다.
2) Input / Output:
- Input: 음성 스트림·계획·사용자 선택.
- Output: 전사·응답·합성 음성·결정 요청.
3) LLM Decision Area:
상대 발언 해석, 다음 질문, 짧은 응답 생성.
4) Code Processing Area:
에코 억제·발화 감지·허용 범위 검사·승인 잠금·발화 취소·녹음 및 시각 동기화.
5) Success Criteria:
필수 항목이 확인되거나 미달성 이유가 분명해진다.
6) Validation Method:
시나리오별 원문 대조, 숫자 되묻기, 승인 이력 검사.
7) Failure Handling:
같은 핵심 정보를 2회 확인해도 불명확하면 사용자에게 전환한다. 겹침·연결 끊김 시 자동 추측을 금지한다. ARS 번호는 사용자가 전화기에서 누른다. 전송 실패 시 직접 입력·준비 문장으로 전환한다.
8) Skills / Scripts:
Skill: 없음. 향후 대화 조정기·정책 검사기·오디오 처리기.
9) Intermediate Artifact Rule:
개발 합성 이벤트는 `output/step03_events.jsonl`. 실제 음성과 식별정보는 Git·공용 로그에 넣지 않는다.

#### Step 04: 결과 확인 및 보관
1) Step Goal:
목적 달성 여부와 다음 행동을 근거와 함께 제공한다.
2) Input / Output:
- Input: 대화 기록·확인 항목·녹음 상태·종료 확인.
- Output: 결과 카드·녹음·누락 및 후속 행동.
3) LLM Decision Area:
요약·미해결 질문·후속 행동 초안 작성.
4) Code Processing Area:
필수 항목 충족 검사·근거 연결·파일 무결성·삭제 예약 관리.
5) Success Criteria:
녹음 실패와 문의 미해결을 각각 표시하고 미확인 사항을 숨기지 않는다.
6) Validation Method:
요약 항목별 원문 근거 대조와 사용자 최종 확인.
7) Failure Handling:
녹음 일부 누락이면 해당 구간 표시. 요약 실패는 원문과 수동 메모로 대체한다. 실제 통화 종료 전 녹음을 임의 종료하지 않도록 확인한다.
8) Skills / Scripts:
Skill: 없음. 향후 결과 검증기·기록 저장소.
9) Intermediate Artifact Rule:
합성 결과는 `output/step04_result.json`. 실제 결과는 사용자별 보호 저장소에 보관한다.

### State Model
| State | Entry Condition | Exit Condition | Next State |
|---|---|---|---|
| `COLLECTING_REQUIREMENTS` | 통화 준비 입력 | 필수 정보 확인 | `PLANNING` |
| `PLANNING` | 질문·허용 조건 구성 | 사용자 확인·점검 통과 | `RUNNING_SCRIPT` |
| `RUNNING_SCRIPT` | 오디오·대화 처리 | 결정 필요 또는 결과 확인 | `NEEDS_USER_INPUT` / `VALIDATING` / `FAILED` |
| `VALIDATING` | 응답 정책 또는 최종 결과 검사 | 검사 완료 | `RUNNING_SCRIPT` / `NEEDS_USER_INPUT` / `DONE` / `FAILED` |
| `NEEDS_USER_INPUT` | 선택·재확인 필요 | 사용자 선택 | `PLANNING` / `RUNNING_SCRIPT` / `VALIDATING` |
| `DONE` | 통화 종료·결과 기록 완료 | 종료 상태 | 없음 |
| `FAILED` | 복구 불가·사용자 중단 | 자동 발화 정지·기록 보존 여부 확인 | 없음 |

앱 런타임에서는 PREPARING / AUDIO_CHECK / LISTENING / THINKING / SPEAKING / WAITING_USER / WRAPPING_UP / COMPLETED / INTERRUPTED를 별도로 사용한다. 위 표는 구현 작업 및 처리 단계의 공통 상태 표현이다.

## 3. Implementation Spec

### Recommended Folder Structure
아래는 초기 제안 구조다. 1차 구현은 `lib/features/call_assist/`의 model/services/view로 구성하고 기존 녹음 서비스와 Apple 플랫폼 재생 채널을 재사용했다. 서버 기반 자동 대화 경로는 아직 구현하지 않았다.

```text
lib/features/call_assist/       # 준비·진행·결과 화면 및 상태
lib/services/call_assist/       # 플랫폼 독립 인터페이스·로컬 기록
server/call_assist/            # 스트리밍 STT·LLM·TTS 조정 및 정책 검사
scripts/call_assist/           # 합성 시나리오 및 지연 측정 도구
output/stepNN_<name>.<ext>      # 개발용 비식별 산출물
```

권장 흐름: 마이크 → 에코 처리·발화 구간 감지 → 스트리밍 STT → 계획/정책 검사 → LLM 응답 → 사용자 승인 검사 → TTS → 스피커. 초기에는 단계가 보이는 구조로 잘못 들은 부분과 잘못 결정한 부분을 구분한다. 음성 직접 입출력 모델은 지연과 통제 가능성을 비교한 뒤 도입한다. API 키는 클라이언트에 고정 배포하지 않는다.

녹음은 단일 마이크 소스에 녹음·인식을 분기한다. 다른 녹음 라이브러리가 마이크를 따로 점유하는 구조를 피한다. 마이크 음원과 생성 음원·실제 재생 시각을 각각 보존하되, 합성 기록을 실제 통화 수신 증거로 취급하지 않는다. 화자 분리는 추정으로 표시한다.

### AGENTS.md Responsibilities
향후 구현 시 저장소 지침에 따라 단일 Codex 에이전트가 작업한다. 승인 규칙·실제 통화 없는 합성 시험·민감정보 로그 금지·플랫폼 실기기 검증을 작업 지침에 명시한다. 이번에는 지침 파일을 변경하지 않는다.

### Custom Agent Definitions
별도 Codex 하위 에이전트는 필요하지 않다. 제품의 통화 AI는 앱 런타임 서비스이며 Codex 자체를 통화 엔진으로 사용하는 설계가 아니다.

### 개발 단계와 비용
아래 기간은 1~2명 개발자가 기존 앱을 활용하고 외부 STT·LLM·TTS를 이용한다는 가정의 계획 추정이다. 계약 견적이나 검증된 개발 일정이 아니다.

| 단계 | 예상 기간 | 산출물·진행 조건 |
|---|---|---|
| 0. 수요·음향 실험 | 1~2주 | 당사자 5~8명 사용 흐름 확인, 기기 조합별 모의 통화 30건 이상 |
| 1. 수동 통화 보조 | 2~3주 | 준비·큰 문장 버튼·직접 입력 TTS·녹음·즉시 중지 |
| 2. AI 추천·승인 | 2~4주 | 실시간 자막·추천 답변·사용자 승인·결과 카드 |
| 3. 제한 자동 대화 | 3~5주 | 일반 절차 문의·대기/전환 대응·정책 검사·실사용 평가 |

합계 약 8~14주를 초기 파일럿 범위로 본다. 공개 출시, 법률 검토, 장기 안정성 시험, 앱 심사는 별도다. 첫 음향 실험에 실패하면 UI 개발을 확대하기 전에 배치·오디오 처리 또는 통신망 연동으로 전환 여부를 결정한다.

운영비는 `STT 음성 처리분 + LLM 입력/출력 토큰 + TTS 발화량 + 서버·저장·전송 비용`으로 계산한다. 공급자를 정하지 않았으므로 분당 가격은 확정하지 않는다. 대기·보류 음악이 많은 고객센터 통화도 포함해 측정한다. 비용 제한에 도달하면 갑자기 통화를 끊는 대신 자동 처리를 멈추고 사용자에게 알린다.

### 대안 비교
| 방식 | 장점 | 과제 | 제안 |
|---|---|---|---|
| 별도 전화기 + 스피커폰 | 기존 번호 유지·통신망 계약 없이 실험 | 소음·에코·두 기기 조작 | 첫 검증 |
| 같은 기기의 통화 음성 추가 | 기기 이동 부담 감소 가능 | 상대 음성 접근·녹음·지원 환경 별도 검증 | 병행 조사 |
| 인터넷 전화·통신망 연동 | 디지털 오디오·발신·종료 관리 가능 | 번호·사업자·운영·법적 검토 | 후속 대안 |
| 기존 문자 발화·사람 중계 | 바로 이용 가능한 대안 | 입력 부담·목적 진행 방식 차이 | 비교 기준·사용자 선택지 |

## 4. Validation Checklist

아래 수치는 제안하는 파일럿 통과 기준이며 현재 달성한 성능이 아니다.

- [ ] 모든 처리 단계의 9개 필드 및 산출물 규칙 확인.
- [ ] 아이패드 실기기, Windows·macOS 목표 브라우저와 iPhone·Android 전화기의 조합을 시험하고 지원표 작성.
- [ ] 정숙·생활 소음·겹침·보류 음악·ARS·화면 잠금·오디오 경로 변경·네트워크 단절 시험.
- [ ] 상대 발화 종료부터 첫 응답 음성까지 p50 2초 이내, p95 4초 이내를 초기 목표로 측정. 목표 미달 시 원인을 분리.
- [ ] ‘즉시 말하기 중지’ 후 로컬 재생 중단 300ms 이내 목표. 대기 중 생성 결과도 나중에 재생되지 않아야 함.
- [ ] 범위 밖 확정·허가 없는 정보 공개·동일 응답 반복 루프는 시험에서 0건. 발견 시 자동 대화 단계로 진행하지 않음.
- [ ] 날짜·시간·인원·비용은 되읽기와 승인 필수. 인식 신뢰도 숫자만으로 확정하지 않음.
- [ ] 녹음을 선택한 시험에서 파일 재생·구간 연속성·AI 출력 시각 확인. 실패를 숨기지 않음.
- [ ] 제한된 기관·고객센터 문의 시나리오 30건 이상에서 근거가 확인되는 목적 달성률 80% 이상을 초기 목표로 측정. 연결 실패·인증 요구·상대 거절·장애·사용자 취소를 분리하고, 전체 시도 대비 달성률과 상담원 연결 후 달성률을 함께 보고.
- [ ] ARS·보류 음악에 불필요한 답변이 나가지 않는지, 장시간 대기 후 상담원 인사를 놓치지 않는지, 부서 전환 후 맥락이 유지되는지 시험.
- [ ] 당사자 5~8명이 준비·진행·중지·결과 확인을 수행. 기존 방법 대비 도움 필요 횟수·입력량·부담 평가.
- [ ] 영구 저장 전 안내·선택, 클라우드 처리 고지, 보관·삭제 및 공급자 정책 검토 완료.
- [ ] 전사 오류로 성공을 과장하지 않는지와 상대가 AI 대화임을 이해하는지 확인.

### 남은 결정
- 첫 시험 기관·고객센터와 구체적인 문의 업무, 주된 아이패드 모델·PC OS.
- 자동화 허용 수준, 최종 확정 승인 방식, 통화당 예상 길이·월 사용량.
- 녹음 필요성·보관 기간·서버 처리 허용 범위.
- 기존 말이음 앱 안에 추가할지 별도 생활 의사소통 앱으로 제공할지. 초안은 기존 앱의 독립 ‘통화 도우미’ 진입점이며 훈련 이력과 통화 기록은 구분한다.
